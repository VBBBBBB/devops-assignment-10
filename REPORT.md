## 1. Introduction & Observability Concepts

Monitoring and observability help teams understand the health and performance of
applications and infrastructure. **Monitoring** tracks predefined indicators, while
**observability** uses metrics, logs, and traces to investigate system behaviour and
diagnose problems. **Prometheus** collects and stores time-series metrics, while
**Grafana** provides dashboards and visualizations to analyze those metrics.

### Three Pillars of Observability
1. **Metrics** - Numerical measurements such as CPU utilization, memory usage, request rate, and error rate.
2. **Logs** - Records of events generated by applications and infrastructure.
3. **Traces** - Show how requests travel through different components of a distributed application.

### Components of Prometheus and Grafana
| Component | Description |
| :--- | :--- |
| **Prometheus Server** | Scrapes and stores metrics. |
| **Exporters** | Expose metrics from systems that Prometheus monitors (e.g. Node Exporter). |
| **PromQL** | Query language used to retrieve and analyze Prometheus metrics. |
| **Grafana** | Visualizes metrics through dashboards and panels. |
| **Alerting** | Notifies teams when defined conditions are met. |

```yaml
  scrape_interval: 15s

  - "alert-rules.yml"

scrape_configs:
  - job_name: "prometheus"
    static_configs:
      - targets: ["localhost:9090"]

  - job_name: "node-exporter"
    static_configs:
      - targets: ["node-exporter:9100"]
```

### 2.2 `prometheus/alert-rules.yml` (excerpt)
```yaml
groups:
  - name: devops-demo-alerts
    rules:
      - alert: HighCpuUsage
        expr: 100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 80
        for: 2m
        labels: { severity: warning }
```

### Step 4: Create the Dashboard
The provisioned dashboard **DevOps System Monitoring** contains three panels:
1. **CPU Utilization** (timeseries)
2. **Memory Usage** (gauge with green/orange/red thresholds)
3. **System Load (1m average)** (timeseries)

### Step 5: Generate Activity and Observe Metrics
```bash
# generate CPU load for ~60 seconds
yes > /dev/null & sleep 60; kill %1
```
Observations during the test:
- **CPU Utilization** rose from ~3% (idle) to ~45% under synthetic load, then fell back after the load stopped.
- **Memory Usage** stayed relatively stable around ~38%, confirming load generation was CPU-bound.
- **System Load (1m)** climbed from ~0.2 to above 1.0 while the load was running.

### Step 6: PromQL Query
A direct PromQL query was executed in the Prometheus expression browser to retrieve a
single metric:
```promql
100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
```
Result (instant query):

### Step 7: Configure an Alert Rule
The alert `HighCpuUsage` fires when CPU utilization exceeds **80% for 2 minutes**:
```promql
100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 80
```
The rule's state was verified under **Alerts** in the Prometheus UI (`Inactive` at
baseline, and it would transition to `Pending`/`Firing` under sustained load).

## 4. Metrics Monitored - Explanation
| Metric | PromQL | Why It Matters |
| :--- | :--- | :--- |
| **CPU Utilization** | `100 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100` | Detects compute saturation and runaway processes. |
| **Memory Usage** | `(1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100` | Detects memory pressure that can lead to OOM kills / swapping. |
| **System Load** | `node_load1` | Indicates overall demand on the CPU (runnable + waiting tasks). |

## 5. Best Practices Applied
1. **Monitor metrics relevant to application health and performance.**
2. **Use meaningful dashboard names and labels** (`DevOps System Monitoring`).
3. **Configure appropriate scrape intervals** (15s balances freshness and overhead).
4. **Avoid exposing monitoring dashboards without authentication** (Grafana admin login enabled).
5. **Set alert thresholds based on expected system behaviour** (80% CPU for 2m), not arbitrary values.
